# Юридический консультант по законодательству РК — дизайн

**Дата:** 2026-08-04
**Статус:** утверждён к планированию

## Задача

Веб-приложение, отвечающее на юридические вопросы строго по действующему законодательству Республики Казахстан, с загрузкой документов, анализом рисков и предложениями по правкам.

Ключевое требование — «только по актуальному законодательству РК» — определяет всю архитектуру: ответы генерируются исключительно из текстов НПА, загруженных с официального источника, каждое утверждение сопровождается ссылкой на статью и датой редакции.

## Что не входит

- OCR отсканированных PDF — не окупается на доступном железе
- Судебная практика — только НПА
- Генерация правленного DOCX с redline — отложено, отчёт со списком правок покрывает потребность
- Аутентификация, мультипользовательский режим, биллинг
- Казахоязычный интерфейс — корпус скрейпится на русском, UI русский

## Источник данных

**ИПС «Әділет»** (adilet.zan.kz) — официальная информационно-правовая система Министерства юстиции РК. Скрейп Playwright'ом в локальный индекс, запускается вручную командой.

Корпус MVP — кодексы и ключевые законы, около 20-25 документов:

- Гражданский кодекс (Общая часть, Особенная часть)
- Трудовой кодекс
- Налоговый кодекс
- Кодекс об административных правонарушениях
- Уголовный кодекс, Уголовно-процессуальный кодекс
- Гражданский процессуальный кодекс
- Предпринимательский кодекс
- Земельный кодекс
- Кодекс о браке (супружестве) и семье
- Закон о товариществах с ограниченной и дополнительной ответственностью
- Закон об акционерных обществах
- Закон о государственных закупках
- Закон о персональных данных и их защите
- Закон о защите прав потребителей
- Закон о жилищных отношениях
- Закон о банках и банковской деятельности
- Закон о разрешениях и уведомлениях
- Закон о правовых актах

Точный список URL фиксируется в `config/sources.yaml` — добавление нового НПА не требует правки кода.

## Ограничения железа

| Ресурс | Факт | Следствие |
|---|---|---|
| GPU | GTX 1650 Ti, 4 GB VRAM | потолок ~4B параметров в квантовании Q4 |
| RAM | 7.8 GB, под нагрузкой почти занята | оффлоад в системную память не вариант |
| CPU | i5-10300H, 4 ядра / 8 потоков | CPU-инференс ~3-5 tok/s, только аварийный фолбэк |
| Диск | 15 GB свободно из 477 | бюджет на модели и индекс жёсткий |

**Выбор моделей:**

- Генерация — `qwen3:4b-instruct` (2.5 GB, установлена). Влезает в 4 GB VRAM при `num_ctx=6144`. Фолбэк при OOM — `qwen2.5:3b-instruct` (1.9 GB).
- Эмбеддинги — `bge-m3` (~1.2 GB, требует загрузки). Мультиязычная, покрывает русский и казахский, 1024 измерения.
- `mistral` и `neural-chat` (4.1-4.4 GB) исключены — не помещаются в VRAM, а свопинг в занятую RAM неприемлем.

Индексация и обслуживание запросов разведены по времени: `bge-m3` работает при сборке индекса, затем выгружается, `qwen3:4b` занимает VRAM единолично. Одновременно обе модели в 4 GB не помещаются.

Дисковый бюджет: bge-m3 1.2 GB + Playwright Chromium 0.45 GB + venv 0.5 GB + индекс ~0.3 GB ≈ 2.5 GB.

**Следствие для качества.** Модель на 4 миллиарда параметров не способна на самостоятельные юридические рассуждения. Поэтому нагрузка переносится на поиск: модель пересказывает найденную норму и сверяет с ней пункт документа, а не рассуждает от себя. Отсюда жёсткое требование обоснования цитатой и отказ при отсутствии релевантного контекста.

`LLM_PROVIDER` в `.env` переключает провайдера на `anthropic` или `openai` без изменения кода — путь к качеству, когда появится бюджет на API.

## Стек

Python-монолит. Один язык, один процесс, база — один файл.

- FastAPI — HTTP и SSE
- SQLite + `sqlite-vec` — векторный поиск и FTS5 в одном файле, без Postgres и Docker
- Jinja2 + HTMX — интерфейс без сборки фронтенда
- Playwright (Python) — скрейпинг
- `python-docx`, `pypdf` — разбор документов
- `pytest` — тесты

Postgres с pgvector отклонён: на корпусе в 25 НПА (оценочно 30-50 тысяч чанков) sqlite-vec даёт поиск за единицы миллисекунд, а отдельный сервис БД добавляет операционную нагрузку без выигрыша.

Отдельный фронтенд на Next.js отклонён: два рантайма и сборка ради чата и формы загрузки файла.

## Архитектура

```
adilet.zan.kz ──[scraper.py, ручной запуск]──> data/raw/*.json
                                                     │
                                        [indexer.py: чанки + эмбеддинги]
                                                     ↓
                                            law.db (SQLite + vec0 + FTS5)
                                                     ↑
                                              [retriever.py]
                                                     ↑
app.py ──┬── GET  /            HTMX UI, две вкладки
         ├── POST /chat        вопрос → retrieve → LLM → ответ со ссылками
         ├── POST /analyze     загрузка файла → job_id
         └── GET  /analyze/{job_id}/events   SSE-прогресс и результат
                                                     ↑
                                   llm.py — провайдер-агностик
```

### Модули

| Модуль | Ответственность | Зависимости |
|---|---|---|
| `config.py` | загрузка `.env` и `sources.yaml`, валидация настроек | — |
| `llm.py` | `complete(messages) -> str`, `complete_json(messages, schema) -> dict`, `embed(texts) -> list[vector]` | config |
| `scraper.py` | Playwright → JSON НПА (заголовок, статьи, дата редакции, URL) | config |
| `indexer.py` | JSON → чанки по статьям → эмбеддинги → law.db | llm, config |
| `retriever.py` | вопрос → top-k чанков с метаданными | llm, law.db |
| `analyzer.py` | DOCX/PDF → пункты → находки | retriever, llm |
| `app.py` | HTTP, SSE, шаблоны | всё выше |

Каждый модуль тестируется изолированно. `llm.py` подменяется фейком в тестах остальных модулей — ни один тест не требует запущенной Ollama, кроме отдельного интеграционного набора.

### Схема базы

```sql
CREATE TABLE acts (
    id            INTEGER PRIMARY KEY,
    title         TEXT NOT NULL,
    adilet_url    TEXT NOT NULL UNIQUE,
    doc_type      TEXT NOT NULL,          -- кодекс | закон | постановление
    revision_date TEXT,                   -- дата редакции с adilet, ISO
    scraped_at    TEXT NOT NULL
);

CREATE TABLE chunks (
    id            INTEGER PRIMARY KEY,
    act_id        INTEGER NOT NULL REFERENCES acts(id),
    article_no    TEXT,                   -- "152" или "152-1"
    article_title TEXT,
    part_no       TEXT,                   -- пункт внутри длинной статьи
    text          TEXT NOT NULL,
    char_len      INTEGER NOT NULL
);

CREATE VIRTUAL TABLE vec_chunks USING vec0(
    chunk_id INTEGER PRIMARY KEY,
    embedding FLOAT[1024]
);

CREATE VIRTUAL TABLE chunks_fts USING fts5(
    text, content='chunks', content_rowid='id'
);
```

`revision_date` показывается в каждом ответе. Без неё утверждение об актуальности непроверяемо.

### Чанкинг

**Чанк — статья НПА, не окно фиксированной длины.** Юридический текст уже структурирован, статья самодостаточна по смыслу, а ссылка «статья 152 Трудового кодекса РК» получается из метаданных, а не угадывается моделью.

Статьи длиннее 2000 символов режутся по пунктам с сохранением заголовка статьи в каждом фрагменте — иначе фрагмент теряет контекст. Статьи короче 100 символов (отсылочные нормы) склеиваются со следующей.

### Ретривер

Гибридный поиск: FTS5 по тексту плюс векторный top-k, слияние по reciprocal rank fusion с k=60.

Чисто векторный поиск проваливается на точных запросах («статья 152 ТК») и на редких терминах. FTS5 входит в SQLite, реализация занимает несколько десятков строк, выигрыш на юридической терминологии существенный.

Порог релевантности проверяется до слияния, по векторной ветке: если косинусная близость лучшего векторного попадания ниже 0.45 и FTS5 не дал ни одного совпадения, ретривер возвращает пустой список — сигнал для отказа от ответа. Значение порога вынесено в конфигурацию и калибруется на наборе контрольных вопросов после сборки полного индекса.

### Промпты и грунтинг

Три правила, зашитые в системный промпт:

1. Отвечай только из переданного контекста. Информации нет в контексте — так и скажи.
2. Каждое утверждение сопровождай ссылкой в формате «статья N <название НПА>».
3. Не додумывай нормы, не обобщай, не переноси знание из других юрисдикций.

Пустой результат ретривера → ответ «Не нашёл релевантной нормы в загруженном корпусе. Уточните вопрос или проверьте, входит ли эта область в список загруженных НПА» с перечнем загруженных документов. Генерация в этом случае не вызывается вообще.

Это единственный способ удержать требование «только законодательство РК» на модели такого размера.

## Анализ документов

Поток обработки:

1. **Извлечение текста.** DOCX через `python-docx` по параграфам с сохранением стилей нумерации. PDF через `pypdf`. Отсутствие текстового слоя в PDF → понятная ошибка о скане, не пустой отчёт.
2. **Нарезка на пункты.** По нумерации (`1.`, `1.1.`, `Статья N`, `§ N`), фолбэк — по абзацам. Пункт становится единицей анализа.
3. **Классификация документа.** Один вызов LLM: договор, устав, приказ, исковое заявление, прочее. Определяет, какие области права применимы, и подмешивается в запросы к ретриверу.
4. **Анализ пунктов.** По каждому пункту: ретрив 3-4 чанков → вызов LLM с JSON-схемой ответа:

```json
{
  "risk": "none | low | medium | high",
  "quote": "точная цитата из документа",
  "norm_ref": "статья 152 Трудового кодекса РК",
  "problem": "что не так",
  "suggestion": "предложенная формулировка"
}
```

5. **Сборка отчёта.** Пункты с `risk: none` отбрасываются. Остальные сортируются по убыванию риска.

Вывод в интерфейсе — текст документа слева, находки справа, привязанные к пунктам подсветкой.

**Производительность.** Договор на 60 пунктов — 60 вызовов LLM, около 3-5 минут на локальной 4B-модели. Поэтому обработка асинхронная: `POST /analyze` возвращает `job_id`, прогресс идёт по SSE. Состояние задач в памяти процесса — при перезапуске теряется, что приемлемо для однопользовательского локального приложения.

**Лимиты.** Файл до 10 МБ, до 300 пунктов. Превышение — явная ошибка с указанием фактического размера.

## Обработка ошибок

| Отказ | Поведение |
|---|---|
| Смена вёрстки adilet | Валидация после парсинга: есть заголовок, есть хотя бы одна статья, текст непустой. Падаем с указанием конкретного URL, в базу мусор не пишем |
| Ollama недоступна | Проверка при старте и перед запросом, понятное сообщение в интерфейсе с командой запуска |
| Модель не помещается в VRAM | Ловим OOM от Ollama, сообщаем про фолбэк на `qwen2.5:3b-instruct` |
| PDF без текстового слоя | Сообщение про скан и отсутствие OCR |
| Пустой индекс | Стартовая проверка, сообщение с командой сборки индекса |
| Невалидный JSON от LLM | Один повтор с уточнением формата, затем пункт помечается как непроанализированный, обработка продолжается |

## Дисклеймер

Присутствует в каждом ответе и в каждом отчёте, не мелким шрифтом в подвале: справочная информация на основе текстов НПА РК, не является юридической консультацией, для принятия решений обратитесь к юристу. Указывается дата последнего обновления корпуса.

## Тестирование

- `test_chunker.py` — нарезка на статьи, длинные статьи, отсылочные нормы, битая нумерация. Фикстуры — фрагменты реальных НПА.
- `test_retriever.py` — RRF-слияние, порог релевантности, точный запрос по номеру статьи. Индекс из трёх статей, эмбеддинги замоканы.
- `test_analyzer.py` — нарезка договора на пункты, разбор ответа LLM, поведение при невалидном JSON. LLM замокан.
- `test_scraper.py` — парсинг сохранённой HTML-страницы adilet, срабатывание валидации на битой странице.
- `test_app.py` — эндпоинты через TestClient, поток SSE, ошибки загрузки файлов.
- `test_integration.py` — сквозной прогон на живой Ollama, помечен `@pytest.mark.integration`, из основного набора исключён.

Playwright используется дважды: в скрейпере и в проверке интерфейса на реальном браузере — загрузка файла, получение отчёта.

## Порядок сборки

1. Каркас репозитория, `config.py`, `.env.example`, `sources.yaml`
2. `llm.py` с провайдером Ollama, загрузка `bge-m3`
3. `scraper.py` на одном НПА (Трудовой кодекс), валидация парсинга
4. `indexer.py` и схема базы, сборка индекса по одному НПА
5. `retriever.py` с гибридным поиском, проверка на реальных вопросах
6. `app.py`, вкладка консультации, сквозной поток вопрос-ответ
7. Скрейп полного корпуса, сборка полного индекса
8. `analyzer.py`, вкладка документов, SSE-прогресс
9. Проверка интерфейса Playwright'ом, обработка ошибок

После пункта 6 система уже отвечает на вопросы — это первая точка, где продукт полезен.
